# Intent: the small places where the code does not mean what it says

Closes #39.

## Problem

Eight items from the 2026-09-24 review, none of them visible to a user today.
That is exactly why they need an argument: a cleanup nobody can justify is
churn. The argument is that this repository's rules lean on the code saying
what it means — argv arrays only, feature detection over assumption, one
mutation at a time — and each of these is a small lie the next reader has to
discover before they can trust the file around it. This session alone has paid
for three of the same shape: a comment claiming `nixString` needed no escaping,
a comment claiming a scan was cheap, and `AGENTS.md` describing checks that did
not exist. Each cost real time to disbelieve.

Two of the eight are defects with a user at the end of them, even though nobody
has reported one. Ranked, those first.

**1. A stream's last line is lost when it has no trailing newline.**
`MicrovmState.qml:663-664` reads both pipes through `SplitParser`, which emits
only on the delimiter. A child that dies mid-line leaves that fragment in the
buffer, and `onExited` (`:669`) appends the `── exit` marker straight after it,
so the log shows the marker where the last line should be. The case this
happens in is a `nixarchy-apply` or a `nix build` that died — and the line it
eats is the one worth reading. `o` opens the log precisely so the user can read
why something failed.

**2. `Model.counts.stopped` is wrong.** `Model.js:632-642`: everything whose
`runtime` is not `"running"` is counted as stopped. The four values the parsers
produce are `"running"`, `"stopped"`, `"failed"` (`Model.js:367,404`) and
`"none"` for a machine nixarchy has not built yet (`Model.js:349,461`), so a
failed VM is counted in both `stopped` and `failing`, and a never-built one is
reported as stopped. Nothing reads the field: `summaryText` (`:644-649`) and
`footerText` (`:651-654`) use `total`, `running` and `pending`;
`Model.listActions` (`:1385-1391`) uses `pending`; and every QML site —
`Panel.qml:84-88`, `MicrovmView.qml:89,385-392,746`, via
`MicrovmState.qml:115` — uses `total`, `running`, `failing` or `pending`. So
today it is a trap set for the next caller rather than a visible bug, which is
the worst of the three states a field can be in.

Then the dead code. Each is a function or a property that claims a job it does
not do:

**3. `MicrovmState.known()`** (`MicrovmState.qml:213-220`) has no callers. Its
comment — "A name typed from outside (IPC) that is not in the list never
reaches a command" — describes a guard, and the guard is applied nowhere.
`Panel.qml:15` does declare an IPC target, `nixarchy.microvm.bar`, so the
sentence reads as a live invariant of a live surface. It is not one, and it
will not become one by itself when a verb finally takes a name.

**4. `Model.parseJsonLines`** (`Model.js:175-186`) is called only from
`tests/model/parsing.test.js:71-74`. A passing test is the strongest signal a
repository has that a function is load-bearing; here it certifies something
nothing uses. `isJsonList` and `parseJsonArray` next to it are the real
`list --json` path.

**5. `MicrovmState.streamKey`** (`:151`) is written by `startStream` (`:291`)
and read nowhere. A property that records which VM a stream belongs to, and is
never asked, invites the assumption that something downstream is keyed on it.

Then two hygiene items:

**6. `appendLog` copies the capped array once per line.**
`MicrovmState.qml:298-303` slices `root.log`, pushes, trims to 400 and
reassigns the `var` property, so a long `nix build` does a 400-element copy and
a full `LogView` model invalidation for every output line. The memory bound is
correct; it is the per-line cost that is not.

**7. `Panel.qml`'s `hideWhenEmpty` never reaches `MicrovmState.settings`.**
`pushSettings()` (`:26-33`) includes the key, but only
`refreshIntervalSec`, `showStopped` and `aiAssist` have change handlers
(`:35-37`). Harmless today — the singleton reads no such key, and `Panel.qml:84`
binds `visible` to `setting()` directly — but it is a declared setting whose
pushed copy silently diverges from the bar's.

**8. Unverified: `MicrovmView.ask()` re-entrancy.** `MicrovmView.qml:240-249`
sets `confirmOpen` and resets `confirmDialog.selectedIndex` with no
`if (root.confirmOpen) return`, so a second question would replace one already
on screen and move the default answer under the user. Whether a second click
can reach `ask()` while `ConfirmDialog` is up (`:809`) depends on whether the
dialog swallows it, and that needs a running shell to say. It was deferred from
#25 for that reason. The one thing that has changed since: the menu is now
enabled on p620, so this is newly testable rather than newly known.

## Proposed outcome

Every one of these reads as what it is. The log keeps the last line of a stream
that died mid-line. A count is either right or absent. A function or property
that exists has a caller, and a comment that describes a guard describes one
that runs. The pushed settings copy matches the bar's. The log path costs what
one line should cost. And `ask()` is either fixed or recorded as tested and
fine — not left as a maybe for a third review to rediscover.

## Affected users and systems

`Model.js`, `MicrovmState.qml`, `MicrovmView.qml`, `Panel.qml` and
`tests/model/parsing.test.js`. Nothing here changes a key, a command or a
surface's appearance, so on the current reading there is no `docs/usage.md` or
README change. The user-facing effect is one: a failed build's last line
appears in the log where today the exit marker is.

## Constraints

- Logic goes in `Model.js` with a Node test; QML stays drawing and wiring. Both
  the buffering fix and anything done to `counts` land as testable functions.
- Deleting a function means deleting its test in the same commit, or the suite
  certifies nothing.
- `counts` is read by QML through `MicrovmState.qml:115` and rendered by
  `Panel.qml` and `MicrovmView.qml`. The `stopped` field itself is read by
  none of them, so changing or removing that one field is not user-visible;
  changing the shape of the object is.
- One mutation at a time, via the singleton: nothing here may add a path that
  touches the lock.
- Item 8 cannot be closed from a checkout. It needs the shell running on p620.

## Open questions

1. **`known()` — delete it, or wire it up?** `Panel.qml` already owns an IPC
   target, and a verb taking a VM name is a plausible next feature. Deleting is
   honest today; wiring it up makes the comment true. Whichever is chosen, the
   comment has to match the outcome.
2. **`counts.stopped` — fix it or remove it?** Nothing reads it, so removing it
   is the smaller diff and cannot regress a caller. Fixing it keeps a field a
   future footer might reasonably want. Doing neither is the one answer ruled
   out.
3. **Does item 8 belong in this task at all?** Everything else here is
   verifiable from a checkout; `ask()` is blocked on a live shell, the same
   blocker as #34. Carrying it makes this PR unmergeable until someone has the
   desktop free.
4. **How far does the log-path change go?** Item 1 is about what reaches the
   log and item 6 about what it costs to put it there. They touch the same few
   lines, so whether they are one change or two affects how each is tested.
